  - Job `candidate` uses concurrency group
    `vyane-rs-candidate-compatibility` with `cancel-in-progress: true`, so a
    newer run cancels an in-progress probe. It records the run start, the
    first failed step name among checkout, uv setup, and
    `Probe current vyane-rs main`, the lock's vyane-rs revision and rmcp
    version, and the upstream main revision from runtime evidence or a fresh
    `git ls-remote`. A probe step outcome of `failure` or `cancelled` is
    recorded under that probe step name. The job does not receive
    `issues: write`.
  - The probe step `timeout-minutes` is 25. The candidate job
    `timeout-minutes` stays 30. A probe that reaches its own limit fails
    that step while the job still has time to record facts and finish as
    `failure`, which the notifier accepts. Checkout and uv setup are not
    separately capped; a hang in either of those steps can still consume the
    job limit, and that job-level timeout is a cancellation, not a failure
    notice.
  - Job `notify` runs only when `github.repository` is `zleo-ai/vyane-paw`,
    `github.ref` is `refs/heads/main`, the event is `schedule` or
    `workflow_dispatch`, the candidate job succeeded or failed, and the run
    is not cancelled (`always() && !cancelled()`). Its own concurrency group
    is `vyane-rs-candidate-canary-notify` with `cancel-in-progress: false`
    and `queue: max`. Notify writes stay serialized, and this group does not
    cancel an in-progress notify when another is waiting. The default queue
    keeps one pending job and cancels the previous waiter; `queue: max`
    keeps up to 100 waiting notifies, in the order they started waiting.
    GitHub cancels further arrivals once that cap is full. `queue: max`
    cannot be combined with `cancel-in-progress: true`. The issue-writing
    step repeats `if: always() && !cancelled()`. A run cancelled before that
    step starts does not write. If cancellation arrives while the step is
    running, that condition becomes false, so GitHub does not keep the
    writer alive beside the next run. A request that has already been sent
    is not withdrawn. The next notify waits until the previous notify job
    has left the group. This was not executed against GitHub; the workflow
    file is what states the rule.
  - Notify permissions are `contents: read` (checkout of the notifier script
    only, `persist-credentials: false`), `actions: read` (one `gh run view`
    of this run), and `issues: write`.
  - `scripts/notify-candidate-canary.sh` asks `gh run view` before any issue
    read or write. A cancelled status or conclusion skips the write and
    exits 0. A failed run-status query exits with that command's status and
    does not create, comment, or close. `gh issue list` is checked the same
    way: a non-zero exit is not parsed and is not treated as an empty list.
  - On failure the script opens one issue labeled `candidate-canary-failure`,
    or comments on the open issues with that label. It does not open a new
    issue when a closed notice already records a newer probe time. The
    failure body records
    the run URL, `Run ID`, `Run attempt`, and `Run time`. `Run time` is the
    candidate job's start-step timestamp, and `Run attempt` is
    `github.run_attempt` captured in that same step. Both are candidate job
    outputs. A notify-only re-run does not re-run the candidate job, so it
    keeps that probe's time and attempt instead of the later notify attempt.
    On success the script comments and closes an open issue only when every
    probe marker in the issue body and comments parses, and every recorded
    probe time is earlier than or equal to this probe's time. Equal times
    close only for the same run id. Run id order is not used. A marker that
    cannot be parsed blocks the close even when another marker is an older,
    readable failure. Trailing CR and trailing whitespace are stripped
    before a marker is matched. A `Run ID` line or a canonical `Run` URL can
    supply the run id; a record with no probe time stays open. The body
    allows only the run URL, run id, run attempt, probe time, failed step
    name, locked vyane-rs revision, locked rmcp version, and upstream
    vyane-rs revision. The run id must be an integer and, when the run URL
    is well formed, must match that URL. A missing or non-integer run id
    aborts before a write. Other fields that are not the expected shape are
    replaced with `unresolved`. Log text is not included. A repository, ref,
    or event outside the rule skips the write.

Ordering uses the candidate job's start-step time, not the run id. The
candidate job also snapshots `github.run_attempt` into
`steps.start.outputs.attempt`. Notify reads
`needs.candidate.outputs.run_attempt` and
`needs.candidate.outputs.started_at`, so a re-run of only the notify job
keeps the probe that already finished. A success closes an issue only when
every probe marker parses and none of those probe times is later. Equal
times close only for the same run id. A marker that does not parse blocks
the close. Trailing CR and trailing whitespace are removed before the
marker is matched.

The notify group keeps `cancel-in-progress: false` and sets `queue: max`.
GitHub's default queue keeps one pending job and cancels the previous
waiter; `queue: max` keeps up to 100 waiting notifies. Past that cap GitHub
cancels further arrivals. This was not executed against GitHub. Because a
queued notify can run after a newer probe has already closed the issue, a
failure does not open a new issue when a closed notice records a newer
probe time.
