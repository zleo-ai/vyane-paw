# VP-13: Durable-workflow control-plane readiness gate

## Status

Implementation and independent review complete; merge gate pending.

## Goal

Eliminate the intermittent `durable control operation was not completed`
failure in the VP-08 integration test by gating the first durable submission
on an explicit workflow control-plane readiness signal, and make any future
occurrence self-diagnosing.

## Dependencies

- Observed failures: PR #8 candidate lane (2026-07-29) and PR #16 stable
  durable-workflow job (run `30518251327`, 2026-07-30). Both passed on
  rerun. The attempt-1 traceback of the stable failure lands at
  `compat/qwenpaw_durable.py:470` — the `workflow-submit` contract check —
  meaning the submit envelope carried a non-`completed` operation status.
- Mechanism: after the QwenPaw application restart, a new MCP server process
  must reconnect its workflow control plane to the resident daemon.
  `wait_for_mcp_tools` proves tool listing works, but the control plane can
  still be transiently `unavailable` when the submit lands. Eight local
  reproduction attempts all passed; the race needs runner-level load.
- Server error taxonomy (pinned vyane-rs `319b9da`): workflow control
  returns `unavailable` while disconnected and `not_found` for a
  well-formed but never-submitted caller id; the plugin envelope preserves
  both codes. The gate additionally relies on the QwenPaw console task
  itself completing during the attach window; if the task ever fails
  instead, the run still fails visibly rather than polling.

## Product contract

- No blanket retries and no masking: only the explicit readiness gate is
  added. Any readiness response other than the expected
  `not_found`/`unavailable`/transport shapes still fails the test
  immediately.
- The readiness wait is recorded in evidence metrics so the transient stays
  visible instead of being silently absorbed.
- No plugin, schema, or contract changes; the probe uses only the existing
  public envelope behavior.

## Acceptance

- `compat/qwenpaw_durable.py` gains a bounded readiness gate before the
  first `workflow-submit`: it polls `workflow-status` for a fixed,
  never-submitted canonical UUIDv7 until the envelope is `rejected` with
  `not_found` (control plane connected). `unavailable` and transport-level
  failures within the time budget keep polling; any other shape fails
  loudly.
- The `assert_contract` failure message includes the operation status and
  error code (never task text), so a future failure is self-diagnosing.
- Evidence metrics record the readiness wait (poll count), and the run
  remains schema-valid.
- `scripts/run-vp08.sh` passes repeatedly locally; CI stable lanes pass;
  the ledger marks this package in progress at implementation time.
- Independent GLM-5.2 review of the exact implementation head returns no
  P0/P1 findings.

## Non-goals

- Retrying the submit itself, changing the plugin's error normalization, or
  altering the upstream daemon/MCP behavior.
- Chasing the remaining theoretical race vectors without observed failures.
