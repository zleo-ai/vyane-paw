# VP-09: MCP capability-negotiation probe

## Status

Implementation and independent review complete; merge gate pending.

## Goal

Produce a reproducible, schema-validated baseline of what the two pinned
endpoints actually advertise and negotiate during MCP initialization:

- the exact `InitializeResult` (protocol version, server capabilities, server
  info, instructions presence) returned by the pinned `vyane-rs` server to a
  client built from the pinned QwenPaw MCP dependency constraints;
- lifecycle parity proof that the pinned QwenPaw `StdIOStatefulClient`
  completes initialization against the same server and observes identical
  server capabilities;
- a bounded method probe for `server/discover`, recording the exact outcome
  (including a standard method-not-found error) without treating absence as a
  failure.

The probe separates three states explicitly in its evidence: `advertised`
(what an endpoint offers), `negotiated` (what the completed handshake
selected), and `product_claimed` (what Vyane Paw claims as a product feature,
always empty in this package).

## Dependencies

- `upstreams.lock.json` pinned revisions (QwenPaw, vyane-rs, rmcp). This
  package does not move the stable lock.
- The locked Python `mcp` SDK in `compat/` (same dependency constraints the
  pinned QwenPaw client uses).
- `schemas/evidence.schema.json` gains one additive scenario
  (`capability_probe`) with scenario-conditional metrics and an optional
  `capabilities` snapshot object. This is a minor, additive change under
  `docs/SCHEMA-MIGRATIONS.md`; no reader of existing scenarios is affected.

## Product contract

- Probe only. This package adds no product capability and changes no plugin,
  policy, or result-contract behavior.
- No MCP Tasks, `server/discover`, stateless, or Streamable HTTP support may
  be claimed anywhere in documentation, skills, or code comments. Evidence
  records observations; claims remain deferred per `docs/STATUS.md`.
- The pinned QwenPaw client module is loaded unmodified, exactly as in VP-01.
  No monkey-patching of QwenPaw or SDK internals. The full `InitializeResult`
  is captured through the SDK's public `ClientSession.initialize()` return
  value in a direct session that uses the same pinned SDK; parity with the
  QwenPaw-wrapped client is asserted via its public session accessor.
- Raw probes that expect an error (such as `server/discover`) record the
  received error code verbatim and never retry, mutate, or "fix" the server.
- Evidence contains no task text, prompts, paths, or deployment values.

## Acceptance

- `scripts/run-vp09.sh` runs the probe on the stable lane against the exact
  pinned revisions and writes `evidence/vp09-capabilities.json`, which
  validates against the extended `schemas/evidence.schema.json`.
- The evidence records: negotiated protocol version; the server capability
  keys verbatim; server name/version from `serverInfo`; whether instructions
  were present; the `server/discover` probe outcome code; QwenPaw-client
  capability parity; clean server shutdown and reaping; and an empty
  `product_claimed` set.
- A negative fixture proves the harness fails visibly when the QwenPaw-wrapped
  client and the direct session observe different server capabilities.
- `docs/MCP-COMPATIBILITY.md` validation-matrix evidence cells for
  `server/discover` and MCP Tasks reference the probe result, with wording
  that states observations only and keeps both rows deferred.
- `scripts/check-repository.sh` passes; the repository CI workflow runs the
  probe as a required stable-lane job; the independent GLM-5.2 review of the
  exact implementation head returns no P0/P1 findings.

## Non-goals

- Implementing or claiming MCP Tasks, `server/discover`, MRTR routing
  metadata, stateless handling, or Streamable HTTP.
- Any plugin, middleware, policy, or operation-result schema change.
- Candidate-lane promotion, lock updates, or upstream changes.
- Bounded workflow output retrieval (blocked on an upstream `WorkflowView`
  projection; tracked as a future package).
