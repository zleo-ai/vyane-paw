# VP-10: Stable upstream lock promotion (vyane-rs rmcp 3.0.1)

## Status

Complete and merged in PR #11.

## Goal

Evaluate the current `vyane-rs` main as a stable-lock candidate and, if every
stable gate passes, promote `upstreams.lock.json`:

- `vyane_rs.revision`: `4848ec4f9d0b740fd8dc5f5586bc30111dc3d373` →
  `319b9da521e3242b482dff46cf92f676b5f38686`
- `rmcp.version`: `3.0.0` → `3.0.1`

The QwenPaw pin (`ebb5b24d0b2559af51d71a38547d88d384357a64`) does not move.

## Dependencies

- Trigger: the VP-06 candidate canary failed on an `rmcp` lock mismatch
  (upstream main resolved `3.0.1` while the lock declares `3.0.0`) in runs
  `30506470381` and `30506842310`. The canary did its job; this package is the
  promotion evaluation it exists to request.
- Upstream delta under evaluation: `4848ec4f..319b9da` — `rmcp` 3.0.1, harness
  permission ceilings with durable-submission preflight, daemon lifecycle
  fixes. The MCP crate surface is unchanged apart from a comment.
- No QwenPaw, plugin, policy, schema, or workflow-script changes are expected;
  any that become necessary must be called out in the pull request explicitly.

## Product contract

- The stable lock moves only on evidence produced at the exact new revision.
  Compatibility is never claimed from version ranges.
- The candidate lane remains advisory; promoting the lock does not change its
  nature.
- If any stable gate fails at the candidate revision, the lock stays put and
  the failure is recorded in this package as the written conclusion.

## Acceptance

- Local evaluation evidence at `319b9da` (runtime evidence, not committed):
  VP-01 smoke, VP-09 capability probe, and the VP-08 real durable lifecycle
  all pass against the candidate build.
- After the lock edit, the full stable gate suite passes at the new revision:
  `scripts/check-repository.sh`, `scripts/run-vp01.sh`, `scripts/run-vp03.sh`,
  `scripts/run-vp09.sh`, `scripts/run-vp07.sh`, and `scripts/run-vp08.sh`.
- Tracked evidence whose content pins the old revision is regenerated and
  committed (`evidence/vp01-baseline.json`, `evidence/vp09-capabilities.json`,
  `evidence/vp03-product-entry.json`, and any drift-checked fixtures).
- `docs/MCP-COMPATIBILITY.md` baseline section names the new revisions.
- CI stable lanes pass on the implementation head and on the merge SHA; the
  advisory candidate canary returns to green once the lock matches upstream
  again.
- Independent GLM-5.2 review of the exact implementation head returns no
  P0/P1 findings.

## Non-goals

- Moving the QwenPaw pin or the `rmcp` version independently of the evaluated
  vyane-rs revision.
- Adopting or configuring the new upstream harness permission ceilings; they
  are evaluated only for backward compatibility with existing flows.
- Claiming any new MCP extension support.
- The deferred items in `docs/STATUS.md` (gateway, packaging, MCP Tasks).
