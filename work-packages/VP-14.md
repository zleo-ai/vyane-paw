# VP-14: Durable readiness budget and failure self-diagnosis

## Status

Implementation and independent review complete; merge gate pending.

## Goal

Make the next durable-workflow control-plane failure self-diagnosing, and
give the readiness gate a budget that matches the observed runner behavior.

## Dependencies

- VP-13 added the readiness gate. Its first live firing (run `30526491370`,
  PR #18 stable durable-workflow) proved the diagnosis was right — the
  submit really was racing an unready control plane — and showed the 30
  second budget is too small for the loaded self-hosted runner: the gate
  polled `unavailable`/transport envelopes until timeout.
- Pinned vyane-rs connects to the daemon per workflow operation
  (`DaemonWorkflowClient::connect` inside submit/status/cancel), so a slow
  or contended daemon accept path surfaces as transient `unavailable` per
  call; a wedged daemon would surface the same way indefinitely. Current
  evidence cannot distinguish the two because runtime logs are deleted
  with the CI workspace.

## Product contract

- Diagnostics before mitigation: on any failure of the integration run,
  bounded tails of the runtime logs are printed to the CI log before the
  process exits. All content in this hermetic run is synthetic by design.
- The readiness budget stays finite and honest: a longer wait with a slower
  poll, never an unbounded one, and the timeout message carries the last
  observed envelope.
- No retries of the workflow operations themselves; no plugin, contract,
  or upstream changes.

## Acceptance

- `compat/qwenpaw_durable.py` prints bounded tails of `qwenpaw-app.log`
  and `data/daemon.log` to the CI-captured output when the run fails,
  before exit.
- The readiness gate budget is raised (120 seconds, one poll per second)
  and its timeout message includes the last envelope.
- `scripts/run-vp08.sh` passes repeatedly locally; evidence stays
  schema-valid; CI stable lanes pass; the ledger marks this package in
  progress at implementation time.
- Independent GLM-5.2 review of the exact implementation head returns no
  P0/P1 findings.

## Non-goals

- Bouncing the MCP client, restarting the daemon mid-run, or changing the
  upstream per-operation connect behavior.
- Widening the accepted readiness envelope shapes defined in VP-13.
